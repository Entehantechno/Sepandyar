# روش‌های کنترل اندروید، صفحه و اپ‌ها — بررسی مبتنی بر گیت‌هاب

> این سند پاسخ به این درخواست است: «در گیت‌هاب روش‌های مختلف کنترل اندروید و
> صفحه‌نمایش و اپ‌ها را بررسی کن و به بهترین روش پیاده‌سازی کن.»
>
> همهٔ داده‌های زیر از **خودِ مخزن‌ها** آمده‌اند (README و metadata از
> `api.github.com` و `raw.githubusercontent.com`)، نه از خلاصه‌های وب.
> ستاره‌ها و تاریخ‌ها مربوط به زمان بررسی‌اند.

## ۱) پنج خانوادهٔ روش

| # | خانواده | نمونهٔ مرجع | ستاره | مکانیزم واقعی |
|---|---|---|---|---|
| ۱ | **نیابت به system server** | `RikkaApps/Shizuku` | ★۳۲٬۹۸۱ | فرایندی با `app_process` بالا می‌آید و اپ‌ها از راه `transactRemote` و `ShizukuBinderWrapper` درخواست را به system server نیابت می‌دهند |
| ۲ | **اسکریپت روی AccessibilityService** | `SuperMonster003/AutoJs6` | ★≈۶٫۳–۶٫۶k | جاوااسکریپت روی درخت گره‌های دسترس‌پذیری، کاملاً روی دستگاه |
| ۳ | **کنترل از کامپیوتر (ADB)** | `openatx/uiautomator2` | ★۸٫۵k | پایتون روی کامپیوتر، دستگاه از راه ADB |
| ۴ | **آینه‌کردن و کنترل صفحه** | `genymobile/scrcpy` | ★≈۱۴۹k | نمایش صفحهٔ دستگاه روی کامپیوتر + ورودی از راه ADB |
| ۵ | **عامل LLM روی دستگاه** | `droidrun/mobilerun` | بنچمارک ۹۱٫۴٪ | اپ «Portal» + AccessibilityService + اسکرین‌شات + مدل زبانی |

### ۱٫۱ Shizuku — قدرتمندترین، و برای ما غیرقابل‌استفاده

توضیح رسمی مخزن: *«Using system APIs directly with adb/root privileges from
normal apps through a Java process started with app_process.»*

یعنی یک فرایند سرور با **روت یا ADB** بالا می‌آید؛ اپ معمولی `binder` آن را
می‌گیرد و هر فراخوانی system API را از راه آن عبور می‌دهد. عملاً «ADB دائمی»
برای اپ‌هاست.

**اما README خودش سه هشدار می‌دهد:**
- *«ADB permissions are limited and different on various system versions»*
- محدودیت Hidden API از اندروید ۹ به بعد
- روی API 26، ADB حتی `registerUidObserver` ندارد

**چرا برای ما رد است:** کاربر باید اول **خودِ Shizuku** را نصب کند و یک‌بار با
Wireless Debugging یا کامپیوتر فعالش کند. برای یک سالمند هفتادودوساله این
غیرممکن است، و Android 17 اساساً sideloading را مسدود می‌کند.

### ۱٫۲ AutoJs6 — دقیقاً همان لایهٔ ما

`AutoJs6` ادامهٔ `hyb1996/Auto.js` است که از **۲۰۲۰-۰۳-۱۳** در نسخهٔ
`4.1.1 Alpha2 build 461` متوقف شد؛ `kkevsekk1/AutoX` هم از ۲۰۲۴-۱۱-۱۴ بی‌تحرک
است. خودِ AutoJs6 فعال است (v6.7.0، ۲۰۲۶-۰۳-۱۴).

اهمیتش برای ما این است که **تنها روش کنترلِ روی‌دستگاهی و بدون کامپیوتر است** —
یعنی دقیقاً همان کاری که لایهٔ ۴ ما می‌کند. و دلیل اینکه هیچ‌کدام از این
پروژه‌ها روی گوگل‌پلی توزیع نمی‌شوند هم همین است.

### ۱٫۳ و ۱٫۴ uiautomator2 و scrcpy — ابزار توسعه، نه محصول

هر دو به یک کامپیوترِ وصل نیاز دارند. برای سالمند معنا ندارند. star بالای
scrcpy نشانهٔ محبوبیتش بین **توسعه‌دهنده‌ها** است، نه کاربران نهایی.

### ۱٫۵ mobilerun — الگوی معماریِ درست، انتقالِ غلط

از README خودش:
- `mobilerun setup` → *«installs the Portal app, enables its accessibility service»*
- *«Combine accessibility trees with screenshots for visual understanding»*
- `--vision-only` → *«useful for the apps that do not have a11y tree information»*
- `--reasoning` → برنامه‌ریزی manager-executor
- **app cards** برای راهنماییِ اختصاصی هر اپ
- پایتون `>=3.11,<3.14`، نیاز به ADB یا اپ Portal

عامل روی **کامپیوتر** و بر بستر ADB اجرا می‌شود. پس انتقالش برای ما غلط است،
ولی **دو ایده‌اش را برداشتیم** (بخش ۴).

## ۲) معیار مقایسه

چهار قید واقعیِ محصول ما:

1. کاربر **سالمند** است — هیچ راه‌اندازی فنی قابل قبول نیست
2. باید از **گوگل‌پلی** توزیع شود
3. **بدون کامپیوتر** و بدون sideloading
4. حریم خصوصی: تصویر صفحهٔ سالمند می‌تواند پیامک و موجودی بانکی داشته باشد

| روش | روی دستگاه، بدون کامپیوتر | قابل توزیع در پلی | شدنی برای سالمند |

| اسکریپت AccessibilityService | ✅ | ❌ برای خودکارسازی | ✅ |
| uiautomator2 / scrcpy | ❌ | — | ❌ |

## ۳) نتیجهٔ شواهد

**هیچ «بهترین روش» واحدی وجود ندارد.** هر روشی که از AccessibilityService
قدرتمندتر باشد، یا به روت نیاز دارد، یا به sideloading، یا به کامپیوتر.

پس بهترین طراحی **یک روش نیست، یک ترتیب است** — همان معماری لایه‌ایِ
قابلیت‌محور که در مراحل ۲۵ تا ۲۷ ساخته شد:

| لایه | فناوری | وضعیت |
|---|---|---|
| ۱ | **AppFunctions** — اپ به سرور MCP روی‌دستگاهی تبدیل می‌شود | ✅ مرحلهٔ ۲۷ |
| ۲ | ML Kit GenAI Agentic API | ⛔ آلفا، نیازمند AICore Developer Preview |
| ۳ | **App Actions / BII** — `shortcuts.xml` | ✅ مرحلهٔ ۲۶ |
| ۴ | **AccessibilityService** محافظت‌شده | ✅ مراحل ۲۳–۲۵ |

چهارچوب حاکم: **دستیارها قابلیتِ اعلام‌شده را صدا می‌زنند، نه پیکسل‌ها.**
کنترل صفحه فقط fallback است.

## ۴) دو شکاف واقعی که این بررسی لو داد

### ۴٫۱ fallback بینایی وقتی درخت خالی است ✅ پیاده شد

mobilerun صریحاً `--vision-only` دارد، و دلیلش را خودش می‌گوید: *«useful for
the apps that do not have a11y tree information»*.

ما `captureForVision()` را داشتیم، ولی **opt-in، سمت وب، و بی‌ارتباط با حلقهٔ
گام‌ها** بود. نتیجه: در یک اپ فلاتر یا canvas، `readScreenText()` خالی
برمی‌گشت، `attempt()` شش بار تلاش بی‌فایده می‌کرد و در پایان
««X» روی صفحه پیدا نشد» می‌گفت — پیامی که **دروغ است**: دکمه هست، ما
نمی‌بینیمش.

**کاری که شد:** در `ScreenTaskRunner.attempt()`، پیش از سوزاندن تلاش‌ها،
خواناییِ درخت سنجیده می‌شود. اگر خالی بود:
- بینایی مجاز باشد → یک بار تصویر خوانده می‌شود و `expect` روی متنِ به‌دست‌آمده
  سنجیده می‌شود (با همان `SmartSelector.normalize`)
- مجاز نباشد → **شکستِ زودهنگام و صادقانه** با پیامی که راه‌حل را می‌گوید،
  نه «پیدا نشد»

سه قید ایمنی که روی آن گذاشته شد:
- **کران فراخوانی** (`MAX_VISION_READS = 2` در هر کار) — چون سرور
  `/api/screen/vision` را به ۶ بار در ۶۰ ثانیه محدود کرده و هر تصویر می‌تواند
  پیامک و موجودی بانکی داشته باشد
- **نخ پس‌زمینه** — هم `captureForVision` با `CountDownLatch` منتظر می‌ماند و هم
  درخواست شبکه blocking است؛ صدا زدنش از نخ اصلی یعنی ANR
- **دروازهٔ `confirm` دست‌نخورده** — بینایی فقط «می‌خواند»، هرگز جای تأیید
  سالمند را نمی‌گیرد

### ۴٫۲ App cards ⛔ در این مرحله پیاده نشد — و دلیلش مهم است

mobilerun برای هر اپ «دانش» دارد تا عامل بهتر کار کند. ما فقط «رسپی»
(فهرست گام) داریم.

**چرا پیاده‌اش نکردم:** سودِ واقعیِ App card در این است که از قبل بدانیم
درختِ دسترس‌پذیری هر اپ خواناست یا نه — تا به‌جای سوزاندن تلاش‌ها، یک‌سره به
بینایی یا به شکستِ صادقانه برویم. ولی **ما آن دانش را نداریم.** بسته‌های هفت
اپِ تأییدشده راستی‌آزمایی شده‌اند، اما کیفیتِ درختِ دسترس‌پذیری‌شان فقط روی
دستگاهِ واقعی قابل سنجش است و این محیط دستگاه ندارد.

پس یک جدول `AppCard` با `treeReadable = false` برای اسنپ و اسنپ‌فود، **دادهٔ
ساختگی** بود — همان دامی که در `CREATE_TAXI_RESERVATION` و
`res/xml/app_metadata.xml` عمداً از آن پرهیز کردیم. ساختارِ بی‌داده ارزشی
ندارد.

**مسیر درستِ پیاده‌سازی‌اش:** وقتی اپ روی دستگاه واقعی رفت، همان
`unreadableScreen()` که در ۴٫۱ ساخته شد، جای طبیعیِ «یادگیری» است — نتیجهٔ
هر کار به سرور برمی‌گردد و می‌توان از `status` و `error`های واقعی، خواناییِ
درختِ هر اپ را استنتاج کرد. App card باید از **مشاهده** ساخته شود، نه از حدس.

### ۴٫۳ حالت استدلال (manager-executor) ⛔ عمداً پیاده نشد

سیاست دسترس‌پذیری گوگل‌پلی (اجرایی از ۲۸ ژانویهٔ ۲۰۲۶) می‌گوید:
*«Any use of the Accessibility API that enables an app to autonomously initiate,
plan, and execute actions or decisions is strictly prohibited.»*

اجازه‌نامه‌ها برای «deterministic, rule-based automation» و «verified
accessibility tools» هستند. یک عامل LLM که خودش روی درخت دسترس‌پذیری
برنامه‌ریزی کند، **دقیقاً** همان چیزی است که ممنوع شده. این یک کمبود نیست؛
یک تصمیم آگاهانه است.

## ۶) جمع‌بندی یک‌خطی
